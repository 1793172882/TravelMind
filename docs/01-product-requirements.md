# 产品需求文档

## 1. 产品定位

TravelMind 不是生成一段旅游攻略的聊天机器人，而是持续管理一次出行任务的 Agent：它查询真实数据、生成可执行计划、验证约束、请求审批、同步外部系统，并在环境变化后恢复任务和重新规划。

一句话描述：

> 面向个人与家庭自由行，通过 Agent Harness 和 MCP 提供可执行、可恢复、可协作的智慧出行服务。

## 2. 目标用户

- 需要安排一日游、周末游或多日自由行的个人。
- 携带老人、儿童等具有明确约束的家庭用户。
- 希望在飞书中共同维护行程的小团队。
- 希望学习 Agent Harness 的开发者，即本项目的第一位开发者和学习者。

## 3. 核心使用场景

### 3.1 创建行程

用户输入目的地、日期、预算、同行人和偏好。Agent主动识别缺失信息，只追问会影响计划的条件，随后查询地点、天气、路线并生成时间表。

验收标准：

- 结果包含每段行程的开始时间、结束时间、地点、交通方式和预计费用。
- 满足用户明确提出的硬约束。
- 每条外部事实带数据来源和查询时间。

### 3.2 修改行程

用户可以用自然语言提出“下午少走一点”“取消灵隐寺”“晚一小时出发”等变更。

验收标准：

- 系统恢复原行程而不是从零生成。
- 只修改受影响的部分。
- 显示修改前后的关键差异。

### 3.3 动态重规划

出发前或行程中发生下雨、景点关闭、用户迟到等情况时，系统重新计算剩余行程。

验收标准：

- 已完成项目不会被重新安排。
- 替代方案继续满足预算、时间和距离约束。
- 外部写入前获得用户确认。

### 3.4 飞书协作

用户通过飞书机器人发起任务，系统通过飞书 MCP创建或更新文档、日历和多维表格。

验收标准：

- Web与飞书共享同一个 `thread_id` 时可以继续同一任务。
- 创建、修改日历或向同行人发送消息需要审批。
- MCP调用失败不会丢失已生成的行程，系统保存待同步任务。

## 4. 功能范围

### 4.1 第一版必须具备

- 多轮需求澄清。
- 结构化行程生成。
- 地点、天气、路线工具。
- 时间、预算、步行距离和营业时间校验。
- 用户审批、中断与恢复。
- 会话Checkpoint和用户偏好记忆。
- Tool Registry、权限、Hooks与错误恢复。
- MCP Client及至少一个测试 MCP Server。
- 飞书 MCP接入。
- 后台任务和定时检查。
- Web API和最小前端。
- Agent轨迹、测试集和演示脚本。

### 4.2 后续版本

- 企业微信、微信公众号、钉钉等入口。
- 更多地图、搜索、酒店或交通 MCP Server。
- 多 Agent：规划、路线、风险、协作等专业 Agent。
- 语义记忆和知识库。
- 团队出行中的多人偏好协商。

### 4.3 明确不做

- 自动付款、抢票和下单。
- 绕过登录、验证码或平台技术限制。
- 非官方个人微信模拟登录。
- 没有数据依据的“实时最低价”承诺。

## 5. 约束分类

### 硬约束

硬约束不满足时，行程不得进入审批：

- 出发、返回时间。
- 总预算上限。
- 必去或禁止地点。
- 最大步行距离。
- 营业时间。
- 地点之间的最小交通时间。

### 软偏好

软偏好用于候选排序，可以在无法全部满足时说明取舍：

- 优先公共交通。
- 喜欢人少、室内或自然景点。
- 饮食口味。
- 希望晚起、少换乘。

## 6. 非功能要求

### 安全

- 密钥只存在服务端配置或秘密管理系统，不进入Prompt和日志。
- 所有外部输入经过Schema验证。
- 高影响工具必须审批。
- 每次工具调用记录用户、线程、工具、参数摘要和结果状态。

### 可靠性

- 普通网络错误有上限重试。
- 外部写入采用幂等键。
- 服务重启后可以恢复等待审批和待同步任务。
- 某个 MCP Server不可用时不影响其他工具。

### 可观测性

- 可以查看每次模型调用、工具调用、重试、审批和状态迁移。
- 可以统计工具成功率、平均耗时、Token成本和约束满足率。

## 7. 成功指标

第一版采用一组固定测试任务评估：

- 硬约束满足率不低于 95%。
- 结构化输出解析成功率不低于 98%。
- 工具失败后任务恢复率不低于 90%。
- 外部高风险写入未经审批执行次数为 0。
- 相同任务在重启后能够从Checkpoint继续。
