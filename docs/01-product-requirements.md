# 产品需求与当前范围

## 1. 产品定位

TravelMind 不是只生成旅游文案的聊天机器人，而是一个能够读取实时出行数据、调用工具、验证约束、保存行程、等待用户审批并连接飞书的单 Agent 应用。

> 面向个人和家庭自由行，用 Agent Harness 管理“模型如何安全、可靠地完成一次出行任务”。

项目的第二目标是学习：通过真实业务理解 LangChain、LangGraph、Harness、MCP、FastAPI 和数据库分层，而不是只写一个聊天 Demo。

## 2. 目标用户

- 需要规划一日游、周末游或多日自由行的个人。
- 携带老人、儿童，具有预算或步行限制的家庭用户。
- 希望从 Web 或飞书发起出行任务的用户。
- 希望用完整项目学习 Agent 工程化的开发者。

## 3. 当前业务场景

### 3.1 Web 智能规划

用户在产品页面输入目的地、时间、预算和偏好。Agent 根据问题调用预算、高德或约束工具，并通过 SSE 展示运行和工具进度。

当前验收点：

- 地点、天气和路线问题必须调用高德工具，工具不可用时不编造实时数据。
- 金额使用确定性预算工具计算。
- 完整候选行程保存前调用约束校验。
- 写数据库、保存偏好或调用飞书写工具时进入审批。
- 使用相同 `thread_id` 可以恢复聊天历史和待审批执行。

### 3.2 行程与日程管理

用户可以在 Web 页面或 HTTP API 中：

- 创建、查看、编辑、删除和归档行程。
- 添加、查看、编辑和删除日程项。
- 查看行程地点的高德静态地图。
- 通过 Agent 在一次事务中保存完整合法行程。

所有查询按当前 `owner_id` 隔离；删除行程时同时删除其逻辑关联日程项并取消未执行的天气任务。

### 3.3 飞书协作

飞书在项目中承担两个方向：

```text
飞书消息 → Webhook/Channel → TravelMind Agent
TravelMind Agent → MCP Client → 飞书消息/文档/日历
```

当前代码支持：

- Webhook challenge、verification token/签名校验。
- 文本消息解析、用户/群聊映射、持久事件去重。
- 飞书中回复“批准/拒绝”恢复待审批工具。
- 通过官方远程 MCP 读取文档。
- 通过官方 `lark-mcp` 发送消息、创建文档和日历事件。
- 飞书回复进入 MySQL Outbox，使用幂等键和有限重试。

真实环境仍需飞书应用权限、应用版本发布、事件订阅及公网 HTTPS 回调。

### 3.4 出发前自动复查

创建带开始时间的行程时，系统生成出发前 24 小时和 2 小时两个 MySQL 定时任务。到期后查询真实天气，调用同一个 Agent 生成调整建议，并保存任务结果；如果行程来自飞书会话，还会主动发送飞书通知。

当前不会自动改写原日程，避免在用户未确认时改变业务数据。

## 4. 功能状态

### 已完成

- 单 Agent 多轮对话、MySQL Checkpoint、暂停与恢复。
- Harness 工具注册、Schema 校验、权限、审批、有限重试和执行事件。
- 高德地理编码、POI、天气、路线和静态地图。
- 时间范围/重叠、预算、步行距离、必去地点校验。
- MySQL 行程、日程、用户、偏好、任务、Outbox、Scheduler 持久化。
- 本地注册登录和用户级数据/会话隔离。
- MCP stdio/Streamable HTTP、动态工具发现和飞书工具接入。
- 飞书入站消息、审批回复、外部写入和天气通知。
- 原生响应式 Web 产品界面。
- 100 条真实 Agent 评测集与 40 项自动化检查。

### 需要真实环境验收

- “飞书提问 → Agent 规划 → 审批 → 创建文档/日历 → 回复消息”的完整链路。
- 100 条评测在真实千问、高德和飞书配置下的最终指标。

### 明确不做

- Docker Compose、CI/CD、云端部署。
- 多 Agent、微服务、Redis、向量数据库。
- 自动付款、抢票、代下单。
- 非官方个人微信模拟登录。
- 酒店/车票实时最低价承诺。

## 5. 业务约束

### 当前确定性硬约束

`backend/app/domain/constraints.py` 已实现：

- 行程结束时间必须晚于开始时间。
- 日程项结束时间必须晚于开始时间。
- 日程项不得超出整体行程时间。
- 日程项之间不得重叠。
- 日程总费用不得超过预算。
- 总步行距离不得超过用户限制。
- 候选日程必须包含全部必去地点。

当前没有实现营业时间、景点关闭、路线换乘缓冲等确定性校验，文档和简历不应把它们写成已完成。

### 软偏好

MySQL Memory 当前保存：

- 最大步行距离。
- 偏好交通方式。
- 饮食限制。
- 是否携带老人。

仅在用户明确表达时调用写工具保存，不根据对话进行敏感信息推测。

## 6. 非功能要求与现状

| 方向 | 当前做法 | 当前边界 |
|---|---|---|
| 安全 | `.env` 隔离密钥、Pydantic 校验、写工具审批、Bearer Token | 没有登录限流、Token 吊销和管理员角色 |
| 可靠性 | Checkpoint、有限重试、Webhook 去重、Outbox、持久 Scheduler | MCP 不会运行时热重连；重启后按配置重建 |
| 一致性 | 行程与日程单事务保存，外部飞书写入最终一致 | 不使用分布式事务 |
| 可观测性 | 请求日志、SSE 执行事件、`/metrics`、`/integrations` | 指标和事件为单进程内存数据，没有 Token/费用追踪 |
| 可测试性 | Fake Model、Fake MCP、Mock 高德、Repository/Service 测试、100 条真实评测 | 完整真实评测需要服务和外部额度 |

## 7. 成功指标

项目不预先承诺没有实测依据的百分比。真实评测脚本会输出：

- 任务完成率。
- HTTP 响应成功率。
- 工具选择准确率。
- 约束满足率。
- 审批触发准确率。
- P50/P95 响应延迟。
- 各业务分类通过率和失败案例。

简历中的数字应来自 `backend/evals/latest_report.md` 的真实运行结果，而不是设计目标。
